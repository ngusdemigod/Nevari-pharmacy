
# Nevari Pharmacy Consultation & Prescription Management Architecture

## 0. Executive Architecture Summary

This system uses **Next.js 14+ with TypeScript** as the primary dashboard UI and **WordPress + WooCommerce** as the commerce, identity, product, order, and payment backend.

A custom WordPress plugin, referred to here as **Nevari Pharmacy Core**, provides:

```text
Next.js Dashboard
      |
      | HTTPS / REST / JWT
      v
WordPress REST API
      |
      v
Nevari Pharmacy Core Plugin
      |
      |-- WooCommerce products, orders, payments
      |-- Custom consultation system
      |-- Prescription management
      |-- Email templates and logs
      |-- Audit logging
      |-- Role-based access control
```

The plugin should avoid replacing WooCommerce functionality. Instead, it should extend WooCommerce where appropriate and use custom tables for pharmacy-specific workflows such as appointments, prescription assignment, email logs, and audit logs.

## 1.2 Data Ownership Model

Use WooCommerce native data for commerce. Use custom tables for workflow-heavy pharmacy operations.

| Domain                        |                                              Storage Strategy | Reason                                            |
| ----------------------------- | ------------------------------------------------------------: | ------------------------------------------------- |
| Users                         |                                               WordPress users | Native authentication, roles, capabilities        |
| Patients                      |                           WordPress users with `patient` role | Can also be WooCommerce customers                 |
| Doctors                       | WordPress users with `doctor` role + doctor profile CPT/table | Need role-based login plus searchable profile     |
| Store admins                  |                       WordPress users with `store_admin` role | Custom operational role                           |
| Products                      |                                          WooCommerce products | Native catalog, stock, pricing, categories        |
| Product categories/tags       |                                        WooCommerce taxonomies | Native dashboard compatibility                    |
| Orders                        |                                            WooCommerce orders | Payments, statuses, refunds, emails               |
| Prescription requirement flag |                                      WooCommerce product meta | Extends product catalog                           |
| Appointments                  |                                                  Custom table | High-volume querying, calendar performance        |
| Prescriptions                 |                                                 Custom tables | Complex lifecycle, item-level product links       |
| Email templates               |                                                  Custom table | Fast rendering, versioning, API-driven management |
| Email logs                    |                                                  Custom table | Searchable delivery/audit history                 |
| Audit logs                    |                                                  Custom table | High-volume, append-only logging                  |
| Custom roles                  |                                  WordPress roles/capabilities | Native WordPress permission system                |

## 1.3 Custom Roles

Create these roles on plugin activation:

```php
add_role('patient', 'Patient', [
    'read' => true,
    'nevari_read_own_profile' => true,
    'nevari_read_own_orders' => true,
    'nevari_read_own_prescriptions' => true,
    'nevari_create_appointment' => true,
]);

add_role('doctor', 'Doctor', [
    'read' => true,
    'nevari_read_assigned_patients' => true,
    'nevari_read_assigned_appointments' => true,
    'nevari_update_assigned_appointments' => true,
    'nevari_create_prescription' => true,
    'nevari_update_own_prescription' => true,
]);

add_role('store_admin', 'Store Admin', [
    'read' => true,
    'manage_woocommerce' => true,
    'edit_products' => true,
    'edit_shop_orders' => true,
    'nevari_manage_doctors' => true,
    'nevari_manage_appointments' => true,
    'nevari_manage_prescriptions' => true,
    'nevari_manage_email_templates' => true,
    'nevari_read_email_logs' => true,
    'nevari_read_audit_logs' => true,
]);
```

Administrators should automatically receive all `nevari_*` capabilities.

```php
register_post_type('nevari_doctor_profile', [
```

## 1.5 Custom Taxonomies

### For Doctors

| Taxonomy                  | Attached To             | Purpose                                   |
| ------------------------- | ----------------------- | ----------------------------------------- |
| `nevari_doctor_specialty` | `nevari_doctor_profile` | Cardiology, dermatology, general practice |
| `nevari_doctor_language`  | `nevari_doctor_profile` | English, Spanish, Arabic                  |
| `nevari_doctor_location`  | `nevari_doctor_profile` | Clinic/region grouping                    |

### For Appointments

Appointments should be stored in custom tables, but controlled values can still be represented as enums or lookup tables. Avoid using WordPress taxonomies for high-volume appointment filtering.

Recommended enum-style values:

```text
appointment_type:
- video
- phone
- in_person
- async_form

appointment_status:
- requested
- confirmed
- checked_in
- completed
- cancelled
- no_show
```

### For Products

Use WooCommerce native taxonomies:

```text
product_cat
product_tag
```

Add a custom badge taxonomy only if badges need flexible management:

```text
nevari_product_badge:
- otc
- prescription_needed
- consultation_required
- controlled_item
```

For strict business rules, use product meta instead of only taxonomy labels.

# 2. Database Schema

## 2.1 Doctor Settings Table

Doctor users exist in `wp_users`. This table stores operational settings that do not belong in post meta.

```sql
CREATE TABLE wp_nevari_doctor_settings (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    doctor_user_id BIGINT UNSIGNED NOT NULL,
    profile_post_id BIGINT UNSIGNED NULL,
    license_number VARCHAR(100) NULL,
    default_appointment_duration INT UNSIGNED NOT NULL DEFAULT 30,
    timezone VARCHAR(100) NOT NULL DEFAULT 'UTC',
    accepts_new_patients TINYINT(1) NOT NULL DEFAULT 1,
    telehealth_enabled TINYINT(1) NOT NULL DEFAULT 1,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY doctor_user_id (doctor_user_id),
    KEY profile_post_id (profile_post_id)
);
```

# 3. Relationship Model

```text
WP User
├── role: patient
│   ├── WooCommerce orders
│   ├── appointments
│   ├── prescriptions
│   └── email logs
│
├── role: doctor
│   ├── doctor profile CPT
│   ├── doctor settings
│   ├── appointments
│   ├── prescriptions issued
│   └── linked patients
│
└── role: store_admin
    ├── manages WooCommerce products
    ├── manages WooCommerce orders
    ├── manages doctors
    ├── manages prescriptions
    ├── views email logs
    └── views audit logs
```

Detailed entity relationship:

```text
patient_user_id ─────┐
                     │
                     ▼
              appointment
                     │
doctor_user_id ──────┘
                     │
                     ▼
              prescription
                     │
                     ▼
        prescription_items
                     │
                     ▼
          WooCommerce product

prescription ─────── optional ─────── WooCommerce order
appointment  ─────── optional ─────── WooCommerce order
```

WooCommerce order linkage:

```text
wc_order.meta:
- _nevari_prescription_id
- _nevari_appointment_id
- _nevari_rx_validation_status

wc_order_item.meta:
- _nevari_prescription_item_id
- _nevari_rx_required
```

# 5. Authentication Endpoints

## 5.1 Auth Endpoint Table

| Method | Endpoint        |           Type | Roles                           | Purpose                                      |
| ------ | --------------- | -------------: | ------------------------------- | -------------------------------------------- |
| `POST` | `/auth/login`   | Business logic | Public                          | Authenticate user                            |
| `POST` | `/auth/refresh` | Business logic | Authenticated via refresh token | Rotate token                                 |
| `POST` | `/auth/logout`  | Business logic | Authenticated                   | Revoke refresh token                         |
| `GET`  | `/auth/me`      |           Read | All roles                       | Return current user profile and capabilities |

### `POST /auth/login`

Request:

```json
{
  "username": "patient@example.com",
  "password": "password"
}
```

Response:

```json
{
  "success": true,
  "data": {
    "access_token": "jwt",
    "expires_in": 900,
    "user": {
      "id": 123,
      "email": "patient@example.com",
      "display_name": "Jane Patient",
      "roles": ["patient"],
      "capabilities": ["nevari_read_own_prescriptions"]
    }
  }
}
```

Validation:

```text
username: required, email or username string
password: required
account status: active
role: must be patient, doctor, store_admin, administrator, or shop_manager
```

Security notes:

```text
- Access tokens should be short-lived, for example 15 minutes.
- Refresh tokens should be stored hashed in wp_nevari_refresh_tokens.
- Refresh tokens should be rotated on every refresh.
- Failed login attempts should be audit logged under SECURITY.
```

# 6. Orders API

Orders are backed by WooCommerce. Access them through WooCommerce CRUD classes, not direct SQL.

## 6.1 Orders Endpoint Table

| Method  | Endpoint                         |           Type | Roles                        | Purpose                          |
| ------- | -------------------------------- | -------------: | ---------------------------- | -------------------------------- |
| `GET`   | `/orders`                        |      CRUD/read | patient, store_admin         | List orders                      |
| `GET`   | `/orders/{id}`                   |      CRUD/read | patient, store_admin         | View order details               |
| `PATCH` | `/orders/{id}`                   |    CRUD/update | store_admin                  | Update order status/notes        |
| `POST`  | `/orders/{id}/notes`             | Business logic | store_admin                  | Add order note                   |
| `POST`  | `/orders/{id}/rx-hold`           | Business logic | store_admin                  | Place order on prescription hold |
| `POST`  | `/orders/{id}/release-rx-hold`   | Business logic | store_admin                  | Release prescription hold        |
| `GET`   | `/orders/{id}/prescriptions`     |           Read | patient, doctor, store_admin | Linked prescriptions             |
| `POST`  | `/orders/{id}/link-prescription` | Business logic | store_admin                  | Attach prescription to order     |

### `GET /orders`

Query:

```text
?page=1
&per_page=20
&status=processing
&patient_id=123
&rx_status=requires_prescription
&date_from=2025-01-01
&date_to=2025-01-31
```

Role behavior:

| Role          | Data Scope                                                                  |
| ------------- | --------------------------------------------------------------------------- |
| patient       | Own orders only                                                             |
| doctor        | No general order listing unless linked to their prescription or appointment |
| store_admin   | All orders                                                                  |
| administrator | All orders                                                                  |

Response:

```json
{
  "success": true,
  "data": [
    {
      "id": 501,
      "number": "501",
      "status": "processing",
      "currency": "USD",
      "total": "152.00",
      "patient": {
        "id": 123,
        "name": "Jane Patient"
      },
      "rx_status": "requires_prescription",
      "prescription_id": 88,
      "created_at": "2025-04-22T12:00:00Z"
    }
  ]
}
```

Validation:

```text
page: integer >= 1
per_page: integer between 1 and 100
status: valid WooCommerce order status
patient_id: store_admin only
rx_status: enum
```

## 13.2 Prescription Visibility Rule

A doctor **cannot view all patients’ prescriptions**.

A doctor can view a prescription only when at least one condition is true:

```text
1. prescription.doctor_user_id equals current_user_id
2. prescription belongs to an appointment assigned to the doctor
3. patient-doctor link exists with status active
4. store_admin explicitly grants temporary review access
```

Patients can view only:

```text
prescription.patient_user_id === current_user_id
AND prescription.status IN:
- assigned_to_patient
- partially_fulfilled
- fulfilled
- expired
- cancelled
```

Patients should not see doctor draft prescriptions.

# 15. Frontend-to-Backend Communication

## 15.1 Recommended Authentication Strategy

Use a **Next.js BFF pattern**.

```text
Browser
  |
  | Cookie session, HttpOnly, Secure, SameSite=Lax
  v
Next.js Route Handler
  |
  | Authorization: Bearer access_token
  v
WordPress Nevari REST API
```

Do not store JWTs in `localStorage`.

Recommended token setup:

| Token         | Storage                                  |   Lifetime | Notes                          |
| ------------- | ---------------------------------------- | ---------: | ------------------------------ |
| Access token  | HttpOnly cookie or Next.js server memory | 15 minutes | Used for REST calls            |
| Refresh token | HttpOnly cookie                          |  7-30 days | Rotated on refresh             |
| CSRF token    | Non-HttpOnly cookie/header               |    Session | Required for browser mutations |

---

## 15.2 Next.js API Client Pattern

```ts
type ApiResponse<T> =
  | { success: true; data: T; meta?: Record<string, unknown> }
  | { success: false; error: { code: string; message: string; details?: unknown } };

export async function nevariFetch<T>(
  path: string,
  options: RequestInit = {}
): Promise<ApiResponse<T>> {
  const response = await fetch(`${process.env.WP_API_BASE}/wp-json/nevari/v1${path}`, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      ...(options.headers || {}),
    },
    cache: 'no-store',
  });

  const json = await response.json();

  if (!response.ok) {
    return {
      success: false,
      error: json.error ?? {
        code: 'request_failed',
        message: 'Request failed',
      },
    };
  }

  return json;
}
```

For server-side route handlers, add the access token from HttpOnly cookies.

```text

```

Inside it, display five tabs:

```text

PAYMENTS
```

```text
Nevari store
```

## 20.6 Audit Event Flow

```text
Application action
  |
  v
Try operation
  |
  |-- success --> write success audit event
  |
  |-- error ----> write error audit event with code/message
  |
  v
Return API response
```

For performance, audit logging should be non-blocking where possible:

```text
Critical event
  |
  |-- write minimal event synchronously
  |-- enqueue metadata enrichment asynchronously
```

Recommended implementation:

```text
- Use direct insert for security-critical logs.
- Use Action Scheduler for non-critical events.
- Never let audit logging failure break checkout or consultation booking.
- If audit insert fails, write to PHP error log as fallback.
```

## 20.8 Audit Retention Policy

Recommended defaults:

| Event Type          | Retention |
| ------------------- | --------: |
| Security events     |   2 years |
| Payment events      |   2 years |
| Order events        |    1 year |
| Consultation events |    1 year |
| Email events        |  180 days |
| Debug/info metadata |   90 days |

Retention job:

```text
Daily scheduled cleanup
  |
  |-- Delete or archive logs older than policy
  |-- Preserve high-severity security/payment logs longer
  |-- Optionally export to external storage before deletion
```

Performance requirements:

```text
- Index category/status/created_at.
- Paginate audit UI.
- Avoid loading metadata JSON in list view.
- Use async logging for high-volume events.
- Batch cleanup deletes in chunks of 500-1000 rows.
```

# 21. WordPress REST Registration Example

```php
register_rest_route('nevari/v1', '/appointments', [
    [
        'methods' => WP_REST_Server::READABLE,
        'callback' => [$appointments_controller, 'index'],
        'permission_callback' => function (WP_REST_Request $request) {
            return current_user_can('nevari_create_appointment')
                || current_user_can('nevari_read_assigned_appointments')
                || current_user_can('nevari_manage_appointments');
        },
        'args' => [
            'page' => [
                'type' => 'integer',
                'minimum' => 1,
                'default' => 1,
                'sanitize_callback' => 'absint',
            ],
            'status' => [
                'type' => 'string',
                'sanitize_callback' => 'sanitize_key',
            ],
        ],
    ],
    [
        'methods' => WP_REST_Server::CREATABLE,
        'callback' => [$appointments_controller, 'create'],
        'permission_callback' => function () {
            return current_user_can('nevari_create_appointment')
                || current_user_can('nevari_manage_appointments');
        },
    ],
]);
```

# 22. Permission Guard Example

```php
final class PermissionGuard {
    public static function can_view_prescription(int $prescription_id, int $user_id): bool {
        $user = get_user_by('id', $user_id);

        if (!$user) {
            return false;
        }

        if (user_can($user, 'nevari_manage_prescriptions')) {
            return true;
        }

        $prescription = Nevari_Prescriptions::find($prescription_id);

        if (!$prescription) {
            return false;
        }

        if (in_array('patient', $user->roles, true)) {
            return (int) $prescription->patient_user_id === $user_id
                && in_array($prescription->status, [
                    'assigned_to_patient',
                    'partially_fulfilled',
                    'fulfilled',
                    'expired',
                    'cancelled',
                ], true);
        }

        if (in_array('doctor', $user->roles, true)) {
            return (int) $prescription->doctor_user_id === $user_id
                || Nevari_Doctor_Patient_Links::exists($user_id, (int) $prescription->patient_user_id);
        }

        return false;
    }
}
```

# 23. Validation and Sanitization Standards

Every API request should follow this pattern:

```text
1. Authenticate request.
2. Authorize by capability and data scope.
3. Sanitize scalar fields.
4. Validate business rules.
5. Use prepared queries or WooCommerce CRUD methods.
6. Return normalized response.
7. Write audit event.
```

WordPress functions to use:

```text
sanitize_text_field
sanitize_email
sanitize_key
wp_kses_post
absint
esc_url_raw
current_user_can
wp_verify_nonce
$wpdb->prepare
```

Never trust:

```text
- user IDs from the request body
- order IDs from the frontend
- prescription IDs from the frontend
- role names from the frontend
- product RX flags from the frontend
```

# 24. Error Handling Standards

Recommended error codes:

```text
unauthenticated
forbidden
validation_error
not_found
conflict
appointment_slot_unavailable
doctor_not_accepting_patients
prescription_expired
prescription_patient_mismatch
product_not_authorized
email_template_not_found
email_send_failed
audit_log_failed
```

Example:

```json
{
  "success": false,
  "error": {
    "code": "prescription_patient_mismatch",
    "message": "This prescription does not belong to the order customer.",
    "details": {
      "order_id": 501,
      "prescription_id": 88
    }
  }
}
```

HTTP mapping:

|  Code | Use                          |
| ----: | ---------------------------- |
| `400` | Malformed request            |
| `401` | Not authenticated            |
| `403` | Authenticated but forbidden  |
| `404` | Resource not found or hidden |
| `409` | Business conflict            |
| `422` | Validation failed            |
| `500` | Unexpected server error      |

For privacy, return `404` instead of `403` when revealing existence would leak patient data.

# 25. Scalability Considerations

## 25.1 Database

```text
- Use custom tables for appointments, prescriptions, emails, and audit logs.
- Add indexes for dashboard filters.
- Use UTC datetime fields.
- Avoid postmeta for high-volume operational data.
- Use WooCommerce CRUD for products and orders.
```

## 25.2 Caching

Cache dashboard aggregations:

```text
store_admin_dashboard_summary: 60-300 seconds
doctor_availability: 30-120 seconds
product_badges: 300-3600 seconds
doctor_directory_filters: 300-3600 seconds
```

Invalidate cache on:

```text
- appointment create/update/cancel
- prescription create/assign/fulfill/cancel
- product RX flag update
- order status update
- email log status update
```

## 25.3 Background Jobs

Use Action Scheduler for:

```text
- sending queued emails
- retrying failed emails
- expiring prescriptions
- audit cleanup
- dashboard aggregation precomputation
- syncing WooCommerce order prescription status
```
